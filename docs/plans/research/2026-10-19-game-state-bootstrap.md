## Creation, transport start and battle start are distinct

| Boundary | Actual authority and behavior | Pinned source |
| --- | --- | --- |
| Lifecycle construction | `GameLifecycle()` has no started state. `start(config)` constructs state in SETUP, logs `lifecycle_started`, returns setup ADVANCED. It does not enter battle. | `src/warhammer40k_core/engine/lifecycle.py:GameLifecycle:556-599; start:599-681`; `engine/game_state.py:GameState.from_config:1704-1720` |
| Formal HTTP creation | `POST /sessions` validates the versioned create payload, builds GameConfig, and calls the common authoritative creation helper. The helper calls facade `start(config)`; transport record starts at revision zero with `started=False`. | `src/warhammer40k_core/adapters/server.py:_create_protocol_session:886-915; _create_authoritative_session:945-976`; `adapters/session_protocol.py:AuthoritativeSession.create:306` |
| Formal transport start | `start_session` drains the existing setup lifecycle to its next decision/terminal boundary, sets `started=True`, and commits status. This can stop at setup choices. | `src/warhammer40k_core/adapters/server.py:_start_protocol_session:989-1015` |
| Accepted decision | Facade finite/parameterized submission resolves the ordinary DecisionRequest; the server then drains accepted ADVANCED status to the next adapter-visible boundary. The local Python facade submission alone does not promise this server drain. | `src/warhammer40k_core/adapters/local_session.py:submit_option:364-371; submit_parameterized_payload:373-386`; `adapters/server_mutations.py:commit_submission_status:87-110; _drain_after_submission:120-134` |
| Battle start | At the final setup step, registered start-battle hooks may first emit ordinary rule decisions. The completion gate must pass before the engine completes setup, enters battle and emits `setup_completion_gate_passed` plus `battle_started`. | `src/warhammer40k_core/engine/setup_flow.py:SetupFlow.advance:399-481`; `engine/setup_completion.py:SetupCompletionGate.complete_setup_and_enter_battle:838-878` |

This is a formal engine-owned battle-start boundary, **not a missing battle-start implementation**. There is no separate client-submitted begin-battle decision or wire command. The contract expressly prohibits synthetic start-battle results, direct `GameState.enter_battle()`, setup-index mutation or lifecycle bypass (`docs/ADAPTER_DECISION_CONTRACT.md:3594-3609`). The gate checks pending decisions/reactions, final setup position, mustering, mission/roles, secondaries, formations, reserves, deployment/coherency, redeploy and prebattle work. Failure returns typed `setup_completion_gate_failed` and leaves setup unchanged; success records pre/post checkpoints and BattleStartRecord.

Exactly five formal command kinds are declared: `start_session`, `advance_session`, `close_session`, `finite_option`, `parameterized_payload` (`src/warhammer40k_core/adapters/command_protocol.py:SessionCommandSubmissionKind:20`). Mutation uses `POST /sessions/{session_id}/commands`; there is no separate setup, begin-game, start-round, start-turn or change-phase kind (`adapters/server.py:_handle_protocol_session:601-679; _apply_protocol_command:792`). Advancing while a decision is pending returns `advance_not_required` (`server.py:_execute_protocol_command:734`). Old-looking formal `/start`, `/advance` or decision paths in some tests are rewritten by the test helper, not real routes (`tests/unit/test_phase18e_server_api.py:_translated_formal_command:2534`).

Legacy compatibility is separate: `POST /games` validates its create schema and invokes the same `start(config)` creation helper, returning setup status201 (`server.py:_create_game:917-943`). `POST /games/{game_id}/advance` drains the lifecycle, marks it started, and commits a noncommand `LEGACY_ADVANCE_SESSION` origin (`server.py:_handle:495-511`). Do not conflate this with formal command identity/revision journaling.

## Setup to turns and phases

- The default setup descriptor is: mustering, mission selection, battlefield creation, attacker/defender, secondary selection, formations, deployment, redeploy, determine first turn, resolve prebattle actions (`src/warhammer40k_core/core/ruleset_descriptor.py:SetupSequenceDescriptor.warhammer_40000_eleventh_default:339-355`). The final step is prebattle actions, not determine-first-turn.
- GameConfig already requires `turn_order`, receives MissionSetup and army inputs, and has no independent first-turn request field (`engine/game_state.py:GameConfig:568-581,621-624`). Inspected `SetupFlow.advance:328-481` has explicit request/processing paths for secondary selection, formations, deployment, redeploy and prebattle, but no explicit branch that rolls or requests mission selection, attacker/defender or first-turn determination. Those supplied config values must not be advertised as an interactive engine roll/selection workflow without additional source/runtime evidence.
- `is_start_battle_boundary` means SETUP and the descriptor's final setup index (`engine/start_battle_hooks.py:233-238`). Legal `GameState.enter_battle` sets BATTLE, round1, active player `turn_order[0]` and phase index0 (`engine/game_state.py:2033-2053`).
- Battle phase order comes from the descriptor. The default is Command → Movement → Shooting → Charge → Fight (`core/ruleset_descriptor.py:BattlePhaseSequenceDescriptor.warhammer_40000_eleventh_default:379-388`). Flow runs round/turn/phase timing hooks and may wait for choices, validates end windows, then calls `advance_to_next_battle_phase` (`engine/battle_round_flow.py:BattleRoundFlow.advance:163-498; _emit_start_timing_windows:585-625`).
- On final phase, turn-end and applicable round-end processing runs; active player advances through turn_order. Completing the last player's turn returns to the first player and increments battle_round (`engine/game_state.py:advance_to_next_battle_phase:2062-2160; _advance_active_player_after_completed_turn:5285-5293`). Game completion is checked against the mission scoring policy's game-length rounds, then emits `game_completed` (`game_state.py:_game_ends_after_completed_round:5510-5515`; `battle_round_flow.py:456-475`).
- Present the authoritative projection's `stage`, `battle_round`, `active_player_id`, `current_setup_step`, `current_battle_phase` and `pending_decision`; do not maintain a second client phase controller (`adapters/projection.py:GameViewPayload:308-335`).
- DecisionRequest carries request ID, decision type, optional actor, payload and finite options. Parameterized requests use the engine sentinel option; finite IDs must be emitted options (`engine/decision_request.py:DecisionRequest:62-119; parameterized_decision_option:123-128`). Request rendering must remain actor/viewer scoped.

## Canonical setup recipe, catalog and RNG authority

The exported formal `contracts/examples/sessions/session-create.json` is generated from `canonical_setup_prebattle_smoke_config`, via `scripts/external_contract_session_examples.py:phase18e_session_examples:19-24,77`; the generator invokes production AdapterGameServer.handle with POST /sessions and start_session in process (30-56). That generator call is not HTTP transport evidence. That factory produces actual setup/prebattle requests from engine state (`src/warhammer40k_core/adapters/setup_smoke.py:32-86`). It supplies fixed player IDs/turn order (75-76), and a selected source-backed mission, terrain, attacker/defender and dispositions (89-99). It deliberately enables legacy non-strict rosters (40) and modifies canonical datasheets with SCOUTS/REDEPLOY (102-137). Describe this as a bounded canonical smoke recipe, not arbitrary army/scenario/full-game certification.

The global catalog provider starts that smoke config solely to project its army catalog (`adapters/server.py:_default_rules_catalog_view:217-220`). `RulesCatalogViewPayload` is content/display dictionaries plus source identity (`adapters/projection.py:222-238`), not a scenario, mission-preset, replay or save-game catalog. No HTTP scenario-list/load endpoint was found in the exhaustive server route dispatch. A future preset chooser needs an explicit client-approved recipe inventory or a separately supported Core API; do not invent a catalog wire field.

GameConfig's fields contain no `rng_seed` (`engine/game_state.py:568-581`). The `rng_seed` at `adapters/contracts.py:AdapterSessionHistoryPayload:40-48` is authoritative history output. The lower-level `DiceRollManager.__init__` accepts `RandomSource | int | str` with no default (`engine/decision.py:254-264`); `RandomSource` converts and stores its supplied seed (`core/rng.py:27-45`). Inspected standard lifecycle call sites supply `state.game_id` (`engine/phases/movement_options_dice.py:389-394`; `engine/lifecycle.py:2027-2030`; `engine/phases/command.py:1266`). Local persistence reconstructs RNG from game_id and authoritative event history (`adapters/local_session.py:_current_rng_state:563-577`). Thus the selected standard facade/HTTP path does not expose an independent client seed input. Do not invent a seed config field or assume two distinct game IDs reproduce the same RNG sequence.

## Projection, replay and persistence are different surfaces

Real formal reads are GET /sessions/{id}, /projection, /catalog, /events, /replay, plus global /rules-catalog (`adapters/server.py:_handle_protocol_session:601-679`; `contracts/openapi.yaml:248 onward; global catalog: server.py:_handle:468-473 and contracts/openapi.yaml:19-38`). Projection is viewer-scoped current state, not an authoritative restore checkpoint. Replay exports are policy constrained; administrator active export is distinct from non-omniscient terminal/closed export (`adapters/server_authorization.py:require_replay_export_allowed:22`).

Python support exists for `LocalGameSession.fork` via GameLifecycle.from_payload, integrity-protected persistence export/import, and ReplayRunner from an initial lifecycle with recorded decisions/checkpoints (`adapters/local_session.py:fork:89-97; to_persistence_payload:99; from_persistence_payload:195`; `engine/replay.py:ReplayRunner:664-755`). Recorded adapter decisions still use ordinary submit functions (`adapters/replay.py:submit_replay_result:28`). Server persistence initialization/export and injected-store recovery are operator APIs (`adapters/server.py:__post_init__:246; initialize_persistence:263; persistence_payload:287`; `adapters/session_recovery.py:recover_server_persistence_payload:91`). There is no HTTP scenario/lifecycle-snapshot/checkpoint/replay import route or corresponding command. Do not promise client load/resume from export merely because Python recovery exists.

The selected `scripts/run_phase18m_reference_server.py:14-44` creates AdapterGameServer with default in-memory/no-store configuration; CLI exposes host, required port and shutdown-file, no scenario/seed/persistence/auth configuration flags. `scripts/run_local_session_dev_server.py:43-76,83-116` is a different read-only movement fixture harness, with no mutation methods.
